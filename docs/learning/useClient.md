# `"use client"` vs server side rendering

**Next.js** components are naturally server components, even React components can be server-side. This means that the components will be "rendered/compiled" in the server (transformed from jsx/tsx to HTML; it's usually worded as "rendered" but rendering means transforming something into an image on my dictionary but anyway) and then only the HTML will be sent to the user (for that component).

Client components are components where the javascript is sent to the user (client) and _then_ they are rendered to HTML. **Or** they may be initially rendered to HTML but then they are _hydrated_ in the client (adding js interactivity to the HTML).

Note that server-side rendering **does not mean** `"use server"`. This directive is mostly used for functions or even modules but it is not about rendering (check https://react.dev/reference/rsc/use-server).

## Why one or the other

Some features require client-specific things. Window-based stuff, some 3rd party APIs, but mainly **effects and state management**, this includes **useState**, **useEffect**, **memo**, **onClick** and others. React will help you tell if a component has to be client-side if you build your project; if you forgot any `"use client"` it will raise an error.

But if the component can be rendered on the server, it allows for a direct exibition at the client, avoiding javascript execution and hydration.

## Can I choose?

If the component requires client-specific behavior, no. In those cases you have to use `"use client"`. _However_, server components can contain client components inside them, so only part of the big picture has to be client-side.

And here's an important distinction, **how you can mix these components**:

- A server component can import a client component and stay server-side;
- When a client component imports a server component, the server component will be rendered client-side;
- A component can be side-agnostic, meaning that it can be client-side or server-side;
- Child-parent component relationships do not guarantee same-side rendering.

## How a component changes side

The rendering side is dictated by the **module dependency tree**, not the rendering tree. So it's the tree generated by the imports, not the uses.

Whenever a component is defined as client-side, the rest of that "branch" is then set as client-side. **But remeber**, this is about the module dependency tree; if a server component is used as a child of a client component but is NOT imported by such client-component, it will still be server-side. Remember the last point on the previous section.

## Limitations

Parent components pass information to the children, but a parent _server_ component has limits on what it can pass to _client_ children components, mainly that the props must be **serializable** such as primitive types, iterables, dates, plain objects (not classes or instances; also not functions).

## What about static generation?

When you build your project, the build is basically rendering every server-side component to HTML and leaving the rest as JS (it also might render client-side components but won't hydrate them, as discussed in the beginning). So "client-side rendering" is still a thing even after build, all rules apply.
